# Интеграция LeakAD → внутренняя CRM

Документ для разработчика LeakAD. Описывает готовый приёмник: адрес, подпись,
формат событий, коды ответов, retry, идемпотентность и акт сверки.

**Адрес вебхука (Контур B, поток изменений):**

```
POST https://functions.poehali.dev/0870a148-8550-4b44-8b4b-9702eddc999a
```

Машиночитаемая схема конверта: `GET .../0870a148-8550-4b44-8b4b-9702eddc999a?r=schema`
(доступна без авторизации).

---

## 1. Безопасность и подпись

Секрет **не передаётся в URL**. Старый ключ, который светился в открытом адресе,
подлежит отзыву — для новой интеграции выпускается отдельный `LEAKAD_SYNC_SECRET`.

Обязательные заголовки каждого запроса:

```
Content-Type: application/json
X-Webhook-Id: <совпадает с event_id в теле>
X-Webhook-Timestamp: <unix seconds>
X-Webhook-Signature: v1=<hex-hmac-sha256>
```

Расчёт подписи:

```
signed_payload = X-Webhook-Timestamp + "." + RAW_HTTP_BODY
signature      = HMAC-SHA256(LEAKAD_SYNC_SECRET, signed_payload)
```

Важно: подпись считается по **сырому телу байт-в-байт**. Пересериализация JSON
после подписи сломает проверку.

Приёмник проверяет: подпись (сравнение в постоянном времени), возраст запроса
(не более 10 минут), уникальность `event_id`, совпадение `X-Webhook-Id` и
`event_id`, `Content-Type`, размер тела (лимит 6 МБ).

## 2. Конверт события

```json
{
  "event_id": "evt_01J8ABCDEF123",
  "event_type": "lead.updated",
  "event_version": 1,
  "transaction_id": null,
  "account_id": "account_123",
  "occurred_at": "2026-09-17T12:45:30.123Z",
  "sent_at": "2026-09-17T12:45:31.005Z",
  "sequence": 18752,
  "entity_type": "lead",
  "entity_id": "lead_987",
  "entity_updated_at": "2026-09-17T12:45:30.123Z",
  "data": {},
  "previous": {},
  "changed_fields": [],
  "raw_snapshot": {}
}
```

`data` должен содержать **полный актуальный объект**, а не только изменения.
Это защищает от рассинхронизации, если предыдущее событие не доехало.

`raw_snapshot` сохраняется целиком, включая поля, которые CRM ещё не умеет
отображать — ни одно поле не теряется.

Поддерживаемые типы событий — см. `?r=schema` → `properties.event_type.enum`.
Неизвестный тип принимается с кодом 200 и пометкой `ignored_unknown_type`:
приёмник не уходит в ретраи из-за события, которого ещё не знает, и сохраняет
сырьё для последующего разбора.

---

## 3. Коды ответов и retry

| Код | Значение | Что делать LeakAD |
|-----|----------|-------------------|
| 200 | Обработано. Тело: `{"ok":true,"event_id":...,"internal_entity_id":...}` | Успех |
| 200 + `duplicate:true` | Событие уже принято ранее | Считать успехом, не повторять |
| 400 | Невалидный JSON | Повтор бесполезен, в журнал ошибок |
| 401 | Подпись не прошла | **Остановить отправку**, уведомить администратора |
| 413 | Тело больше 6 МБ | Разбить событие |
| 415 | Неверный Content-Type | Исправить отправитель |
| 422 | Валидный JSON, нарушена схема | В журнал ошибок / DLQ, без автоповтора |
| 503 | Временная ошибка приёмника | Повторять по retry-политике |

Ожидаемая retry-политика на стороне LeakAD:
1 мин → 5 мин → 15 мин → 1 час → 6 часов → 24 часа → далее каждые 24 часа до 7 суток,
затем Dead Letter Queue с возможностью ручного перезапуска.

---

## 4. Идемпотентность и порядок

- `event_id` уникален; повторная отправка того же `event_id` возвращает
  `duplicate: true` и **не создаёт вторую сущность**.
- Постоянные внешние ID (`lead_id`, `contact_id`, `comment_id`, `task_id`,
  `file_id`, `payment_id`) — единственный ключ связи. Телефон, имя и текст
  комментария идентификаторами не считаются.
- Событие с более старым `entity_updated_at`/`sequence` **не перезаписывает**
  более свежую версию карточки — ответ 200 с `action: skipped_stale`.
- Разрывы `sequence` приёмник детектирует сам:
  `GET ...?r=gaps&account_id=...&key=<secret>` вернёт список пропущенных
  диапазонов, которые нужно дослать через ваш `/api/export/v1/events`.

## 5. Первичный импорт (Контур A)

Пакетная загрузка выгрузки, идемпотентная — повторный прогон той же пачки
дублей не создаёт.

```
POST .../0870a148-8550-4b44-8b4b-9702eddc999a?r=import&key=<secret>
Content-Type: application/json

{
  "entity": "leads",          // leads|contacts|comments|tasks|files|payments|
                              // pipelines|statuses|users|sources|custom-fields
  "account_id": "account_123",
  "snapshot_at": "2026-09-17T12:00:00Z",
  "items": [ ... ]
}
```

Ответ содержит `imported`, `received` и построчный список ошибок с индексом
и внешним ID — ни один объект не теряется молча.

Рекомендуемый порядок: справочники → контакты → заявки → комментарии и задачи
→ файлы → сверка.

---

## 6. Файлы

Метаданные приходят событием `file.created`; приёмник сам скачивает файл по
`download_url`, проверяет `sha256` и перекладывает в своё хранилище.

Требования к ссылке: доступна серверу без браузерной сессии, живёт не менее
24 часов (лучше 7 суток), повторно выдаётся по `file_id`.

Если sha256 не сошёлся — файл **не сохраняется**, запись помечается
`sha_mismatch`, событие при этом принимается (данные не подменяются).
Не забранные файлы добираются повторно:
`POST ...?r=refetch-files&key=<secret>` с телом `{"limit":25}`.

## 7. Акт сверки

```
GET .../0870a148-8550-4b44-8b4b-9702eddc999a?r=checksums&account_id=...&key=<secret>
```

Ответ: `counts` (в т.ч. `deleted_*`), `sums` (суммы договоров и платежей,
строкой до копейки), `hashes` по каждой коллекции.

Правило формирования hash — сравнивается с вашим `/api/export/v1/checksums`:

```
record_hash     = sha256(canonical_json(record))   // ключи отсортированы, без пробелов, UTF-8
collection_hash = sha256(join("\n", sorted(record_hashes)))
```

---

## 8. Наблюдаемость

| Метод | Назначение |
|-------|-----------|
| `?r=status&account_id=...` | счётчики событий, последний `sequence`, разрывы, необработанные, DLQ, состояние файлов |
| `?r=events&outcome=failed,dead_letter` | журнал событий с фильтрами по outcome / entity_id / диапазону sequence |
| `?r=gaps&account_id=...` | пропущенные номера sequence |
| `POST ?r=replay` | ручной повтор события из журнала/DLQ по сохранённому payload, без участия LeakAD |

Все служебные методы требуют `key=<secret>` либо токен сотрудника CRM.
Секреты и полные номера телефонов в технические логи не пишутся.

---

## 9. Sandbox

Тестовый прогон ведётся на `account_id` с префиксом `sandbox`, `test_`,
`acct_e2e` или `demo_`. Такие события обрабатываются полностью, но карточки
не попадают в рабочую воронку и вычищаются одной командой:

```
POST ...?r=purge-sandbox&key=<secret>   {"account_id": "sandbox_..."}
```

Боевой `account_id` эта команда отвергает — снести рабочие данные ей нельзя.

---

## 10. Версионирование

Текущая версия — `event_version: 1`. Новые необязательные поля можно добавлять
без смены версии. Удаление, переименование или смена типа поля требуют новой
версии; старая поддерживается минимум 90 дней после объявления новой.
Событие с неподдерживаемой версией получает 422 и список поддерживаемых версий.

---

## 11. Что осталось за LeakAD

Приёмник готов и протестирован. Со стороны LeakAD по ТЗ требуется:

1. Read-only API экспорта (`/api/export/v1/...`) либо полный ZIP/JSONL-экспорт.
2. Постоянные внешние ID для всех сущностей.
3. Полный снимок объекта в каждом событии (`data`, не только изменения).
4. `sequence`, монотонный в пределах `account_id`, и хранение событий ≥ 30 дней.
5. Метод выдачи событий по диапазону sequence.
6. HMAC-подпись по правилу из раздела 1 и новый секрет безопасным каналом.
7. Retry-политика и DLQ.
8. Метод `/checksums` для акта сверки.
